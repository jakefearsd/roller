## What Package B shipped, task by task

### B1 — One status-pill component (commit `cc3d22175`)
`WEB-INF/jsps/editor/StatusPill.jsp`, a `<jsp:include>` callers drive with
**request**-scoped `pillStatus` (a `PubStatus` name) and optional `pillWhen`
(a `Date`, for `SCHEDULED` rows) — request scope because `<jsp:include>`
runs in a fresh `JspContext`. Renders `<span class="status-pill
status-<lower>">` plus a `.status-when` when `pillWhen` is set. Replaced
Bootstrap badges, `tr`/`td` row-tint classes and a separate legend paragraph
on `Entries.jsp`/`Pages.jsp` with one five-variant component
(published/draft/pending/scheduled/trashed) plus a sixth (`status-unsaved`)
reserved for a later editor use. A `<c:remove>` on every non-`SCHEDULED`
branch stops `pillWhen` leaking across `forEach` iterations (request scope
persists across the loop). `A_OWNED` files skip in `stock, unstyled
Bootstrap colors` until Package A merges and picks the component up — that
skip, and the comment explaining it, live in `JspConsistencyTest`.

### B2 — Three button buckets (commit `eff1317b5`)
Every admin button is now `btn-primary` (one recommended action per
screen), `btn-danger`, or `btn-secondary` — `btn-success` retired as a
fourth bucket. `btn-success → btn-primary` where it was the screen's one
recommended action; bare `class="btn"` → `btn-secondary` tree-wide;
`<input type="button" class="btn...">` converted to real `<button>`
elements. `Entries.jsp`'s delete-confirm "Yes" and `MediaFileView.jsp`'s
"Delete selected" both land on `btn-danger`; "Move selected" is explicitly
`btn-secondary` per the brief. Same `A_OWNED` skip/comment convention as B1.

### B3 — One selection bar (commit `eb0d233c5`)
`.selection-bar` (`data-selection-bar="<form id>"`, `hidden` by default,
header checkbox carries `data-select-all`) on Entries/Submissions/
MediaFileView. `roller.js`'s delegated `change` listener counts checked
boxes per form and writes the count via the new `selection.count` message
(`"{0} selected"`, all eight bundles). **Controller ruling recorded rather
than invented**: `Trash.jsp` gets no bar — `TrashController` has only
per-row and whole-trash endpoints, no `restoreSelected`/`deleteSelected`
pair.

### B4 — Native date inputs; jQuery UI leaves entirely (commit `e61b2b049`)
`EntriesSidebar.jsp`'s start/end filters go from a `readonly` text input
plus jQuery UI's `datepicker()` to native `<input type="date">`.
`EntriesBean` parses `ISO_LOCAL_DATE` first, falls back to the legacy
`MM/dd/yy` format so a bookmarked search URL still works. A pre-change grep
confirmed this was jQuery UI's only consumer anywhere in the admin UI, so
the whole dependency — the webjar in `app/pom.xml`, two `<script>`/`<link>`
lines in `head.jsp`, and a 99-line `.ui-datepicker` dark-mode override block
in `roller.css` — came out clean.

### B5 — Entries list feel and the date tag (commits `4a75d5ae4`, round-1 fix `bab1aa387`)
Title cell becomes the primary link to the editor (pencil column and its
header deleted — the title does that job now); a `.entry-meta` line under
it carries the anchor plus, for `PUBLISHED` rows, a **View** link.
`EntriesController.statusChipUrls` builds one URL per status carrying every
current filter, not just the status swap. New `<rc:date>` tag
(`app/.../ui/tags/DateTag.java`, declared in the existing
`rollerConfig.tld`, prefix `rc`) replaces `fmt:formatDate` (server zone) and
`weblogEntryQuery.date.toStringFormat` (request-locale zone) with one
renderer: `datetime` is absolute UTC (machine-readable), the visible text
is the **weblog's** wall clock in `Locale.ROOT` (tabular data, not
localized prose). **Round-1 fix, found in code review**: the initial chip
implementation used `fn:escapeXml` to close an XSS gap but missed that
`URLUtilities.getQueryString` concatenated key/value pairs **raw** —
`fn:escapeXml` cannot repair a parameter split (`&` starts the next param,
`#` truncates everything after it, `+` round-trips as a space). Fixed at
the source: `getQueryString` now runs both key and value through
`URLUtilities.encode`, fixing every caller at once (pagers, feeds, search,
previews, the bulk redirect, the chips) — with a from-the-encoder-side
re-audit (not just the original sink-side grep) catching `FeedModel`, the
one caller the first pass missed. `weblogEntryQuery.date.toStringFormat`
was **not** deleted: `EntryEdit.jsp:533` (A-owned) still resolves it.

### B6 — Sidebars on the rail's grammar (commit `2de86632f`)
Five sidebar JSPs' `.card`/`.card-body` become `<aside class="sidebar">`
with `.sidebar-group`/`.sidebar-label` blocks — the same caps-label role
the admin rail itself uses. Every sidebar form gets `.form-stacked`.
`MediaFileSidebar.jsp`'s "Add new folder" becomes one real `.input-group`
submit (the old `onCreateDirectory()` JS function and its keydown handler
deleted). This commit was amended once to fold in a B5 hold-back item.

### B7 — One modal shape; `data-confirm` everywhere (commit `ade903d73`)
Scope discovery found the true footprint was wider than the brief's file
list: ten files carry `confirm(` calls or modal markup once a blanket grep
was run, not four. Every inline `window.confirm()`/`onclick="return
confirmX()"` became `data-confirm` on the triggering control;
`Members.jsp` (whose removal-confirm depends on which radio in a whole
table is checked, not on one button) keeps a form-level `data-confirm` and
introduces `data-confirm-when` — an optional CSS selector the submit
handler checks before prompting (`!when || matches`). Every `.modal-title`
is now a `<p>`, never a heading element, and every `.modal-footer` puts the
dismiss button before the destructive/primary one.
`JspConsistencyTest.oneConfirmIdiomAndOneModalShape` pins all four rules
(`confirm(` banned, `onsubmit=` banned, `.modal-title` tag, footer order)
outside `A_OWNED`.

### B8 — Errors point at the field (commit `9090ba558`)
`BaseController.addFieldError(model, fieldId, key, request)` (plus an
`Object[] args` overload) adds the same message `addError` does, plus the
control's DOM id into `invalidFields`/`invalidFieldIds`. All three admin
layouts conditionally render `<body data-invalid-fields="...">`; `roller.js`
marks (`.is-invalid`, `aria-invalid`) and focuses the first named field on
`DOMContentLoaded`, fully null-guarded (this script also loads on public
weblog pages). Converted across `WeblogConfigController`,
`CreateWeblogController`, `CategoryEditController`, and others named in the
report's controller→field-id table. **Explicitly skipped as instructed**:
`EntryEditController` (`entry_bean_pubTimeLocal`) — Package A owns that file;
M1 covers it.

## Deferred items and open follow-ups, across the whole package

Nothing shipped in Package B was deferred without a stated reason — see
each task's own report for its "self-review" section — but three items are
worth restating here because they cross into M1's scope specifically:

1. **A9's `Pages.jsp` list-view permalink URL is a genuine 404, and it is
   still live on this branch too.** Package A's own report
   (`2026-09-09-package-a.md`, deferred item 3) found that every published
   page's row links to `${urls.weblogAbsolute(actionWeblog)}page/${p.slug}`,
   which 404s — the same bug A9 fixed on the editor's own permalink line
   but not here. **B11 fixed a related but different bug at the same
   line** (`7e0813edd`): the slug was unescaped, an XSS hole. B11's fix
   wraps `${p.slug}` in `fn:escapeXml(...)`, matching `PageEdit.jsp`'s own
   escaping — but it did not change the URL's *shape*, so if A9's diagnosis
   of a 404 is correct, that defect is orthogonal to B11's fix and still
   present after both packages merge. M1 should compare `Pages.jsp`'s href
   construction against whatever A9 changed on `PageEdit.jsp`'s permalink
   line and reconcile the two.
2. **Every A-owned file (`EntryEdit.jsp`, `EntryEditor.jsp`, `PageEdit.jsp`)
   needs B's five conventions applied, and `A_OWNED` needs emptying.**
   Collected from each task's report: status pills (B1) render in stock
   unstyled Bootstrap colors there today; the three button buckets (B2)
   are unconverted; `<rc:date>` (B5) is not used — `EntryEdit.jsp:533`
   still resolves `weblogEntryQuery.date.toStringFormat` via
   `fmt:formatDate`, and that key cannot be deleted until it converts;
   the one-modal-shape/`data-confirm` rules (B7) are unchecked there
   (`JspConsistencyTest.oneConfirmIdiomAndOneModalShape` explicitly skips
   `A_OWNED`); and `EntryEditController`'s `entry_bean_pubTimeLocal` field
   error (B8) was explicitly left unconverted, named in the brief as
   Package A's file. Once these five are applied, `JspConsistencyTest`'s
   `A_OWNED` set should shrink to `Set.of()` (or be deleted outright) and
   every scan that currently skips it should be re-run to confirm it still
   passes with the skip removed — several of these tests were written to
   fail loudly on exactly this class of regression, and a forgotten skip
   would silently keep them blind on the merged files.
3. **`weblogEntryQuery.date.toStringFormat` key deletion** — blocked on
   item 2's `<rc:date>` conversion of `EntryEdit.jsp`; do not delete the
   key until that conversion lands, or the JSP resolves nothing where a
   timestamp used to render (Velocity/JSP leniency: a missing key does not
   throw, see CLAUDE.md's Templates section).

None of the three above are regressions introduced by Package B — the
first predates both packages (found by A, only partially addressed by an
unrelated B fix at the same source line), and the other two are the
intentional, brief-directed consequence of B running in a worktree that
cannot touch Package A's files.
