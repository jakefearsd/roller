# W5 — Soft delete / trash Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deleting an entry from the authoring UI moves it to a trash the
author can undo from, while removing it from every reader-facing surface
immediately.

**Architecture:** A fifth `WeblogEntry.PubStatus` value, `TRASHED`, plus a
nullable `weblogentry.trashed_at`. Every query that names a status excludes
trash by construction; the one query path that names none —
`WeblogEntrySearchCriteria` — gets a default that excludes it. The authoring
UI's single deletion seam, `BaseController.removeEntryWithIndex`, becomes
"move to trash"; `WeblogEntryManager.removeWeblogEntry` stays the permanent
delete behind "delete forever", the purge sweep, and weblog deletion.

**Tech Stack:** PostgreSQL 16 + JPA/EclipseLink, Spring MVC, JSP/JSTL,
Bootstrap 5 + the Quiet Instrument tokens, Lucene, JUnit 5,
Selenide/Selenium.

**Spec:** `docs/superpowers/specs/2026-08-13-w5-trash-design.md`. Read its
first two sections before Task 1 — the whole design exists to keep the new
dimension in two places, and a change that adds a third is the failure mode.

## Global Constraints

- **Never push.** Commit per task as each task's final step says.
- Work directly on `master`. No feature branch.
- **This wave owns migration `V025` and no other number.** Idempotent DDL;
  never edit an applied migration.
- **`it-selenium/src/test/resources/seed-it-data.sql`** is raw SQL with no
  compile-time or JPA check. `V025` only adds a column so the usual failure
  mode does not apply, but check it anyway and report what you found.
- **A new route means a new `it-selenium/.../support/Routes.java` entry**, with
  its content-tile CSS marker, in the same commit — `RouteSweepIT` visits every
  route and asserts the marker, because Roller renders full site chrome whether
  or not the content tile is wired up at all.
- **New message keys go in the base bundle only**
  (`app/src/main/resources/ApplicationResources.properties`) and must be
  referenced by a JSP or controller **in the same commit** — `MessageKeyTest`'s
  orphan ratchet refuses keys nothing references. Its
  `KNOWN_DYNAMIC_KEY_COUNT` may only ever move DOWN.
- **The apostrophe rule** at the top of the bundle: double an apostrophe ONLY
  for keys invoked *with* arguments.
- **No hex colour literals in CSS** — `DesignTokenTest` fails on any hex that
  does not trace to `roller-ui/styles/roller-tokens.css`.
- **Author-controlled EL must be escaped** — `EditorJspEscapingTest` walks
  every JSP and fails on a listed expression rendered raw. `entry.title` is on
  that list.
- **Velocity is lenient here**: a template reference to a deleted Java member
  prints as literal text with no error and no failing test. Adding an enum
  value cannot trip this, but grep before deleting anything.
- **Controllers must name `@RequestParam`/`@PathVariable` explicitly** — the
  build does not pass `-parameters`; `ControllerMetadataTest` enforces it.
- Run the **full** unit suite each task in the FOREGROUND: `mvn -q -pl app test`.
  Baseline entering this wave: 3042 tests, 0 failures, 3 pre-existing skips.
- Read test counts from the surefire/failsafe **XML reports**, never Maven's
  console text.

### Task 1: The status, the column, and the one exclusion

**Files:**
- Create: `bin/db/migrations/V025__entry_trash.sql`
- Modify: `app/src/main/java/org/apache/roller/weblogger/pojos/WeblogEntry.java`
- Modify: `app/src/main/resources/org/apache/roller/weblogger/pojos/WeblogEntry.orm.xml`
- Modify: `app/src/main/java/org/apache/roller/weblogger/pojos/WeblogEntrySearchCriteria.java`
- Modify: `app/src/main/java/org/apache/roller/weblogger/business/jpa/JPAWeblogEntryManagerImpl.java`
- Check: `it-selenium/src/test/resources/seed-it-data.sql`

**Interfaces produced, for every later task:**
- `WeblogEntry.PubStatus.TRASHED`
- `WeblogEntry.getTrashedAt()` / `setTrashedAt(Timestamp)` — nullable
- `WeblogEntrySearchCriteria.isIncludeTrashed()` / `setIncludeTrashed(boolean)`,
  **default false**

- [ ] **Step 1: The migration**

Find the migration that creates `weblogentry` (grep `bin/db/migrations/`) and
use its real column-naming style. Then:

```sql
-- Migration: soft delete for weblog entries.
--
-- trashed_at is nullable and carries no default: NULL means "not in the
-- trash", and the stamp exists only so the purge sweep and the trash list can
-- order and expire. The trash state itself lives in weblogentry.status as
-- PubStatus.TRASHED rather than in this column, because every query that
-- names a status then excludes trash by construction instead of needing a
-- condition that fails open when forgotten.

ALTER TABLE weblogentry
    ADD COLUMN IF NOT EXISTS trashed_at timestamp with time zone;
```

Match the type to how other timestamps on this table are declared — read them
rather than trusting `timestamp with time zone` here.

- [ ] **Step 2: The enum value and the field**

`WeblogEntry.java:65` — `public enum PubStatus {DRAFT, PUBLISHED, PENDING, SCHEDULED}`
gains `TRASHED`. Add `private Timestamp trashedAt;` with accessors in the
surrounding style, and map it in `WeblogEntry.orm.xml` beside the other
timestamps.

**Add TRASHED last in the enum declaration.** Check how `status` is persisted
(`orm.xml`, look for an `@Enumerated` equivalent): if it is stored by
`ordinal()` rather than by name, adding a value is safe only at the end, and if
it is stored by name the position does not matter. Say which it is in your
report — this is the kind of thing that is silently fine until it is a data
migration.

- [ ] **Step 3: The one exclusion**

`WeblogEntrySearchCriteria` gains `private boolean includeTrashed = false;`
with accessors.

In `JPAWeblogEntryManagerImpl.getWeblogEntries` (around line 510, where
`wesc.getStatus()` is applied), the logic becomes:

- an explicit status is set → filter to it exactly, as today. A caller asking
  for `TRASHED` gets trash; a caller asking for anything else cannot get trash,
  which is the property the whole design rests on.
- no explicit status, `includeTrashed` false (the default) → append
  `AND e.status <> ?n` bound to `PubStatus.TRASHED`.
- no explicit status, `includeTrashed` true → no status condition at all.

Write the comment that explains why the default is false, in terms of what
breaks if it is not: a new caller that thinks about nothing must get the safe
behaviour, because the unsafe direction puts deleted entries on a public page.

- [ ] **Step 4: Leave the four unfiltered named queries alone**

`WeblogEntry.getByCategory`, `getByWebsite&Anchor`,
`getByWebsite&AnchorOrderByPubTimeDesc` and `getByWebsite` name no status and
**must keep seeing trash**. The spec's table gives the reason for each. Add a
one-line comment to each in `WeblogEntry.orm.xml` saying so, so the next person
to add `AND w.status <> TRASHED` "for consistency" reads why not first.

Verify there is no *sixth* status-less query path: grep the manager and the orm
for entry queries and check each against the spec's table. Report anything the
spec missed.

- [ ] **Step 5: Tests**

At the manager level, which is the level that matters:

- an entry set to `TRASHED` is absent from `getWeblogEntries` with a
  default-constructed criteria
- ...and present when `includeTrashed` is true
- ...and present when the criteria asks for `TRASHED` explicitly
- a criteria asking for `PUBLISHED` never returns it
- `isWeblogCategoryInUse` still returns true for a category whose only entry is
  trashed (a trashed entry still holds its category)
- the anchor of a trashed entry is still taken — creating a new entry with the
  same title does not reuse it

- [ ] **Step 6: Run `SchemaMigrationTest`, then the full suite**

`mvn -q -pl app test -Dtest=SchemaMigrationTest`, then `mvn -q -pl app test`.
If `ReflectionTest`/`EqualsContractTest`/`PojoComparatorTest` enumerate
`WeblogEntry`'s properties, update them here.

- [ ] **Step 7: Commit**

```bash
git commit -am "A deleted entry stops being visible without stopping existing"
```

### Task 2: Trashing, restoring, and deleting forever

**Files:**
- Modify: `app/src/main/java/org/apache/roller/weblogger/business/WeblogEntryManager.java`
- Modify: `app/src/main/java/org/apache/roller/weblogger/business/jpa/JPAWeblogEntryManagerImpl.java`
- Modify: `app/src/main/java/org/apache/roller/weblogger/ui/controllers/BaseController.java`

**Interfaces:**
- Consumes Task 1's `TRASHED` and `trashedAt`.
- Produces on `WeblogEntryManager`:
  - `void trashWeblogEntry(WeblogEntry entry)` — status `TRASHED`, stamp now, save
  - `void restoreWeblogEntry(WeblogEntry entry)` — status `DRAFT`, stamp null, save
  - `List<WeblogEntry> getTrashedEntries(Weblog weblog)` — newest-trashed first
  - `int purgeTrash(Weblog weblog, int retentionDays)` — hard-deletes entries
    trashed longer ago than that; returns the count; `-1` purges nothing

- [ ] **Step 1: The manager methods**

`removeWeblogEntry` is unchanged — it stays the permanent delete. Build the new
methods beside it, going through the same `strategy` and `saveWeblogEntry`
paths the rest of the class uses. `purgeTrash` calls `removeWeblogEntry` per
entry so there is exactly one permanent-deletion path.

**Restore sets `DRAFT`, never the previous status**, and the comment must say
why: an undelete that silently republishes to feeds, the sitemap and every
subscriber is a worse outcome than one extra click.

- [ ] **Step 2: `removeEntryWithIndex` becomes "move to trash"**

`BaseController.removeEntryWithIndex` (line ~313) is already the single seam
the authoring UI deletes through — `EntriesController`'s bulk action and
`EntryRemoveController`'s two paths all call it. Read its javadoc first: it
explains the index dance (re-index as DRAFT so the index drops the document,
then `removeEntryIndexOperation` if it was published, then
`CacheManager.invalidate`).

Keep every one of those steps and replace only the final
`removeWeblogEntry(entry)` with `trashWeblogEntry(entry)`. Rename the method to
say what it now does, and update its three callers and its javadoc.

**The index steps are not optional and not redundant** just because the entry
still exists: a `TRASHED` entry left in the Lucene index is findable by site
search and links to a page that 404s, which is the exact failure the javadoc
already describes.

Add a sibling that does the permanent version — the same index and cache steps
plus `removeWeblogEntry` — for Task 3's "delete forever" to call.

- [ ] **Step 3: Tests**

- trashing sets status and stamp, and does NOT hard-delete
- trashing removes the entry from the search index (assert against the index
  manager, the way the existing tests for this seam do — find them first)
- restoring sets DRAFT and clears the stamp
- restoring a *published* entry still yields DRAFT, asserted explicitly with a
  comment naming the hazard
- `purgeTrash` hard-deletes past the retention, keeps within it, and purges
  nothing at `-1`
- trashing does not create an entry revision (status is not content — verify
  against `weblogentry_revision`, do not assume)

- [ ] **Step 4: Full suite, then commit**

```bash
git commit -am "Delete means trash; forever means forever"
```

- [ ] **Step 1: The runtime property**

`entry.trash.retention.days`, integer, default `30`, in the display group the
other entry-related settings live in (find where `entry.revisions.retention`

This is a **new** runtime property, not a promotion, so the
two-files/DB-row-wins traps in CLAUDE.md's Configuration scope section do not

- [ ] **Step 2: The task**

Read `ScheduledEntriesTask` and follow it exactly — the same base class,
registration and configuration shape. Per weblog, call
`purgeTrash(weblog, retention)`. Log the count when non-zero, nothing when
zero.

Failures are logged, never propagated: this runs off the scheduler, and a
failed purge must not take the task runner down.

The task's own logic, with retention set to `-1`, `0` and a positive value.
CLAUDE.md notes that observing `ScheduledEntriesTask` end-to-end costs minutes
of real time; do not try to observe the schedule — test the work the task does,

### Task 5: Prove the reader cannot see it

**Files:**
- Create: `it-selenium/src/test/java/org/apache/roller/it/TrashIT.java`
- Create/modify: a rendering test for the surfaces below

**This is the task the wave exists for.** Everything else is machinery; this is
the assertion that a deleted entry is actually gone from the places a reader
looks. Four of the five surfaces are safe by construction (they filter
`PUBLISHED`), and a test that says so is what stops someone "simplifying" the
criteria default later.

- [ ] **Step 1: Rendering-level tests**

A published entry, then trashed, must be absent from: the weblog home page,
its own permalink (404, not a 500 and not a rendered draft), the Atom feed,
and the sitemap. Find the existing rendering tests for each of those four
surfaces and add a trashed case to each rather than building a new harness —
`ScheduledEntryIT` does exactly this shape for a future-dated entry and is the
model to copy.

- [ ] **Step 2: Site search**

A trashed entry must not be returned by site search. This one is NOT free by
construction — it depends on Task 2 having de-indexed it. Assert it.

- [ ] **Step 3: `TrashIT`**

Delete an entry from the Entries screen; find it in Trash; confirm its
permalink 404s; restore it; confirm it comes back **as a draft** and not as a
published post; then delete it forever and confirm it is gone from Trash.

- [ ] **Step 4: `mvn -q verify -Pit -Dit.test=TrashIT -Dsurefire.skip=true`**, then the whole
  browser suite. `-DskipTests` would also skip failsafe; use `-Dsurefire.skip=true`.
  A 409 at `docker-maven-plugin:start` means a stale container:
  `docker rm -f roller-it-postgres`. `ReferenceError: EasyMDE is not defined`

### Task 6: Document it

**Files:**
- Modify: `CLAUDE.md`

- [ ] **Step 1: Write the Trash section**

Cover, in the voice of its neighbours:

- **Why a fifth `PubStatus` and not a `deleted_at` column**: every query that
  names a status excludes trash by construction, so the new dimension does not
  spread. A `deleted_at` condition fails *open* — forget it and deleted entries
  reappear on a public page.
- **The exclusion lives in exactly one place**, `WeblogEntrySearchCriteria`'s
  `includeTrashed` default of false, and the default is the safety property.
- **The four status-less named queries that deliberately still see trash**, and
  the reason for each: a trashed entry still holds its category and its anchor;
  its permalink 404s anyway because `TRASHED != PUBLISHED`; and deleting a
  weblog must take its trash with it.
- **Restore goes to DRAFT, always** — an undelete that republishes is worse
  than an extra click, and it is why no column remembers the previous status.
- **`removeEntryWithIndex`'s successor is still the one authoring-side deletion
  seam**, and the index steps are still not optional: a trashed entry left
  indexed is findable by site search and links to a 404.
- **Pages and media files are deliberately NOT in the trash**, with the reason
  (a soft-deleted media file still occupies disk, still counts against quota,
  still has a rendition ladder, and is still reachable at its URL unless every
  one of those learns about trash — the spreading this design exists to avoid).
- **`entry.trash.retention.days`**, runtime, default 30, `-1` for forever.

- [ ] **Step 2: Re-check neighbouring claims**

The Entry-editing section describes delete as removing the entry. Fix anything
this wave made false.

- [ ] **Step 3: Commit**
